# 하네스 구축·관리

템플릿 원본: `C:\Users\CARROT I\Desktop\WorkSpace\harness-template` (아래에서 `{T}`)

하네스는 두 층으로 이루어진다.
- **공통 기반** — 모든 프로젝트에 같은 것: planner / reviewer / tester, `/harness-plan`·`verify`·`handoff`·`evolve`, 훅. `install.ps1` 이 설치하고 업데이트 때 교체한다.
- **도메인 팀** — 프로젝트마다 다른 것: 대도메인 AI Agent 안의 세부 유형에 맞춘 `team-*` 에이전트와 워크플로 스킬. 이 스킬이 인터뷰를 거쳐 생성하고, 업데이트 때 보존한다.

## 원칙
- 하네스는 나만 쓰는 개인 도구이고, 프로젝트는 팀이 함께 진행한다. 프로젝트의 `CLAUDE.md` 와 `settings.json` 은 건드리지 않고, `*.local.*` 파일과 `harness-`·`team-` 접두사 파일만 쓴다. 이 파일들은 `.git/info/exclude` 로 제외해 팀 저장소에 흔적을 남기지 않는다.
- 하네스는 내 변경에만 작동한다 (HARNESS.md 의 "내 작업 범위"). 설정도 이 원칙에 맞춘다.
- 코드에서 알 수 있는 것은 묻지 않는다. 코드로 알 수 없는 것(목표, 우선순위)만 묻는다.
- context 문서와 팀 정의에는 코드에서 확인한 사실만 쓴다. 확인하지 못한 내용은 "확인 필요"로 남긴다.
- 생성하는 모든 문서는 사용자가 대화에 쓰는 언어로 쓴다. 템플릿이 한국어라는 이유로 다른 언어 사용자에게 한국어 문서를 만들지 않는다.
- context 문서는 매 세션 로드된다. 파일당 대략 80줄 이내로 쓴다.

## 0. 현황 점검
1. 대상은 현재 프로젝트 루트다. 확실하지 않으면 사용자에게 확인한다.
2. `.harness/` 가 있으면 `powershell -NoProfile -ExecutionPolicy Bypass -File "{T}\doctor.ps1" -Target "<루트>"` 를 실행한다.
3. 요청과 상태로 절차를 고른다.

   | 상태 / 요청 | 실행할 단계 |
   |---|---|
   | 처음 등록 | 1 → 7 전부 |
   | 업데이트, `domain.md` 가 미작성 | 1, 그다음 3 → 7 (2는 비어 있는 문서만) |
   | 업데이트, 도메인 팀 있음 | 1, 6 → 7 |
   | 에이전트 추가 | 4 (추가분만, 기존 팀과 겹치는지 확인) → 5 → 6 → 7 |
   | 유형 변경·팀 재구성 | 3 → 7. 기존 `team-*` 중 남길 것과 지울 것을 사용자에게 확인 |
   | 점검 | "점검" 절 |
   | 제거 | "제거" 절 |

4. 처음 등록할 때 충돌을 확인한다.
   - `.claude/agents/` 에 프로젝트 고유 에이전트가 있으면 역할을 읽어 둔다. 4단계에서 겹치는 역할은 새로 만들지 않고 그 에이전트를 팀 표에 연결한다.
   - 프로젝트 `CLAUDE.md` 에 이미 규칙이나 절차가 있으면 context 문서에 반복하지 않고 "CLAUDE.md 참고"로 남긴다.

## 1. 공통 기반 설치
```
powershell -NoProfile -ExecutionPolicy Bypass -File "{T}\install.ps1" -Target "<루트>"
```
- 기본으로 `.git/info/exclude` 에 ignore 블록을 쓴다. git 저장소가 아니면 `.gitignore` 로 대신한다. 사용자가 `.gitignore` 에 넣기를 원할 때만 `-UseGitignore` 를 붙인다.
- 출력의 `MODE`, `VERSION`, `ADDED_FILES`, `CONFIG_KEYS_ADDED`, `IGNORE`, `UNFILLED_CONTEXT` 를 확인한다. 버전이 바뀌었으면 `{T}\CHANGELOG.md` 의 해당 항목을 요약해 알린다.
- `GITIGNORE_BLOCK_REMOVED` 가 있으면, 예전 버전이 `.gitignore` 에 넣었던 하네스 블록을 지웠다는 뜻이다. `.gitignore` 변경은 팀에 보이므로 사용자에게 알리고, 커밋할지는 사용자가 정하게 한다.
- doctor.ps1 의 `tracked` 가 FAIL이면 하네스 파일이 이미 git에 들어가 있다. `git rm -r --cached <경로>` 로 추적을 끊자고 제안한다. 이 변경도 팀에 보이므로 사용자 확인을 받는다.
- 저장소의 커밋 계정(`git config user.name`, `user.email`)을 확인해 보고한다. 비어 있거나 이 저장소에 맞지 않아 보이면(회사 저장소인데 개인 이메일 등) 알린다. git 계정 설정은 하네스가 바꾸지 않고, 사용자가 원할 때만 설정한다.

## 2. 프로젝트 분석
`UNFILLED_CONTEXT` 에 있는 `project.md`, `architecture.md`, `conventions.md` 를 채운다.
- 매니페스트, 진입점, 디렉터리 구조, 린터·포매터 설정, 기존 테스트를 실제로 읽는다. 코드베이스가 크면 영역별 탐색을 Explore 서브에이전트에 병렬로 맡기고 결론만 받는다.
- 다 채우면 `harness:unfilled` 주석을 지운다.
- `.harness/harness.config.json` 의 `format` / `lint` / `test` 를 실제로 있는 도구로 채우고 한 번씩 실행해 확인한다. 동작하지 않는 명령은 비워 두고 이유를 보고한다. 편집할 때마다 훅이 실패하기 때문이다.
- `format` 과 `lint` 는 반드시 파일 단위로 쓴다 (`{file}`, 예: `npx prettier --write {file}`). 편집 훅은 `{file}` 이 없는 명령을 실행하지 않는다. 프로젝트 전체 format은 팀원 파일을 바꾸고, 전체 lint는 팀원 코드의 오류로 내 작업을 막기 때문이다.
- `verifyOnStop` 은 테스트가 대략 30초 안에 끝날 때만 true로 제안한다.

이 단계는 3단계 인터뷰를 기다리지 않아도 된다. 인터뷰 질문을 먼저 보내고, 답을 기다리는 동안 진행해도 좋다.

## 3. 도메인 인터뷰
`references/ai-agent-domains.md` 의 1장을 따른다. **세부 도메인은 매번 묻는다.** 코드에서 추론했더라도 건너뛰지 않는다. 같은 스택이라도 무엇을 만드는지는 코드만으로 알 수 없다.
1. 매니페스트와 디렉터리에서 스택, 평가 체계, 유형의 단서를 먼저 추론한다.
2. 세부 도메인을 선택지 없이 열린 질문으로 묻는다 (1-2절). 추론한 내용은 질문 앞에 밝힌다. 답을 요약해 되물어 확인한다.
3. `AskUserQuestion` 으로 단계 / 품질 우선순위 / 팀 규모를 묻는다 (1-3절).
4. 답을 1-4절 표에 따라 구성 요소로 옮긴다.

## 4. 팀 설계
`references/ai-agent-domains.md` 의 2~3장과 `references/team-design.md` 의 1~3장을 따른다.
1. 세부 도메인의 핵심 동작마다 품질을 책임질 역할을 정한다. 3장에 비슷한 유형 예시가 있으면 출발점으로 쓰고, 없으면 공통 역할 + 도메인 전용 역할을 직접 설계한다. 단계, 우선순위, 규모로 조정한다. 공통 역할은 재사용하고, 0단계에서 찾은 기존 에이전트와 겹치는 역할은 만들지 않는다.
2. 각 에이전트의 모델을 업무 성격으로 고른다. 모두 opus로 지정하지 않는다.
3. 기본 루프(plan → verify → handoff)로 충분하지 않은 반복 흐름이 있을 때만 도메인 워크플로 스킬을 설계한다.
4. 설계안을 사용자에게 보여주고 확인받는다.

   | 에이전트 | 맡는 일 | 모델 (이유) | 호출 시점 | 실행 모드 |
   |---|---|---|---|---|

   설계안에 대한 피드백은 반영해 다시 보여준다. 파일을 만든 뒤 고치는 것보다 싸다.

## 5. 팀 생성
`references/team-design.md` 의 4~5장 템플릿으로 만든다.
- 에이전트: `.claude/agents/team-{role}.md`. 원칙에는 이 프로젝트에서 확인한 경로, 명령, 패턴을 넣는다. 일반론만 있으면 기본 에이전트와 다를 게 없다.
- 워크플로 스킬 (설계했을 때만): `.claude/skills/team-{name}/SKILL.md`. 0단계(이전 실행 확인), 단계별 실행 모드, 데이터 전달, 오류 처리, 테스트 시나리오를 넣는다.
- 읽기 전용 검토자는 `disallowedTools: Edit, Write, MultiEdit, NotebookEdit`.

## 6. domain.md 연결
`.harness/context/domain.md` 를 채운다 (`team-design.md` 6장).
- 도메인, 팀 표 (모든 `team-*` 를 백틱으로), 루프 연결 (조건 → 에이전트 → 목적), 도메인 워크플로, 도메인 점검, 변경 이력 첫 줄.
- `/harness-plan` 과 `/harness-verify` 는 이 파일의 "루프 연결"을 읽고 팀을 호출한다. 여기 적지 않은 에이전트는 호출되지 않는다.
- 다 채우면 `harness:unfilled` 주석을 지운다.
- 업데이트일 때는 새 버전의 공통 기반과 루프 연결이 여전히 맞는지만 확인한다.
