# AI Agent 도메인 카탈로그

대도메인은 AI Agent(LLM 기반 에이전트·애플리케이션 개발)다. 이 문서에는 세부 도메인을 묻는 인터뷰, 코드에서 찾을 신호, 유형별 팀 구성 예시가 있다.

**카탈로그는 선택지가 아니라 참고 자료다.** 세부 도메인은 매번 사용자에게 열린 질문으로 묻는다. 3장의 유형은 비슷한 도메인을 설계할 때 출발점으로만 쓰고, 맞는 유형이 없으면 사용자의 설명에서 직접 팀을 설계한다. 도메인을 카탈로그 유형에 끼워 맞추면 그 프로젝트에만 있는 핵심 작업을 놓친다.

## 목차
1. 인터뷰
2. 공통 역할
3. 유형별 구성 예시 (A~E, 혼합)
4. AI Agent 공통 점검 항목

## 1. 인터뷰

### 1-1. 묻기 전에 코드에서 추론한다
코드로 알 수 있는 것을 물으면 사용자의 시간을 낭비하고, 사용자가 잘못 기억한 답이 코드보다 우선하게 된다. 매니페스트(`package.json`, `pyproject.toml`, `requirements*.txt`, `go.mod` 등)와 디렉터리 구조부터 본다.

| 신호 | 추론 |
|---|---|
| `@anthropic-ai/sdk`, `anthropic` | Claude API 직접 사용 |
| `@anthropic-ai/claude-agent-sdk`, `claude_agent_sdk` | Claude Agent SDK |
| `langgraph`, `langchain`, `llama_index`, `crewai`, `autogen`, `pydantic_ai` | 에이전트 프레임워크 |
| `openai`, `google-genai`, `mistralai`, `ollama` | 다른 공급자 |
| `pgvector`, `chromadb`, `pinecone`, `qdrant`, `weaviate`, `faiss`, 임베딩 호출 | RAG |
| `@modelcontextprotocol/sdk`, `mcp`, 도구 스키마 정의 | 도구 사용 / MCP |
| 여러 에이전트 정의, 그래프·노드, handoff, supervisor | 멀티에이전트 |
| `.claude/skills/`, `.claude/agents/`, `.claude-plugin/`, 훅 스크립트 | Claude Code 확장 |
| `livekit`, `twilio`, `realtime`, 오디오 스트림, STT/TTS | 음성·실시간 |
| `evals/`, `promptfoo`, `inspect_ai`, `braintrust`, `langsmith`, `ragas` | 평가 체계 있음 |
| `prompts/`, 템플릿 파일, 코드 안의 긴 문자열 프롬프트 | 프롬프트 관리 방식 |

코드가 거의 없으면(새 프로젝트) 스택도 질문에 넣는다.

### 1-2. 질문 1 — 세부 도메인 (열린 질문, 매번)
선택지를 주지 않고 평문으로 묻는다. 선택지를 주면 사용자가 자기 도메인을 가장 가까운 칸에 끼워 넣어, 정작 중요한 특징이 사라진다.

> 어떤 AI 에이전트를 만드는 프로젝트인가요? 아래를 자유롭게 알려 주세요.
> - 무엇을 하는 에이전트인지, 누가 쓰는지
> - 에이전트가 하는 핵심 동작 (예: 문서 검색 후 답변, 외부 시스템 조작, 여러 에이전트 협업, 코드 생성…)
> - 지금 가장 어렵거나 자주 틀리는 부분

코드에서 추론한 내용이 있으면 질문 앞에 "코드를 보니 ~로 보입니다"라고 먼저 밝히고, 맞는지와 빠진 것을 함께 묻는다. 답을 받으면 한두 문장으로 요약해 되물어 확인한다. 이해가 틀린 채로 설계하면 팀 전체가 틀어진다.

### 1-3. 질문 2 — 조건 (AskUserQuestion)
도메인을 확인한 뒤 `AskUserQuestion` 한 번에 묻는다.

1. **단계** — 새로 만든다 / 기존 에이전트를 개선한다 / 운영 중 품질 문제를 해결한다
2. **품질 우선순위** (복수 선택) — 답변 정확성·근거 / 안전성·권한 / 비용·지연 / 평가 자동화·재현성
3. **팀 규모** — 가볍게 (1~2명 추가) / 표준 (3~4명) / 철저하게 (검증 역할 강화)

사용자가 코딩 경험이 적어 보이면 assertion, LLM-judge, 궤적 같은 용어를 설명 없이 쓰지 않는다. 답이 모호하면 한 번만 되묻고, 그래도 모호하면 표준 구성으로 시작해 `/harness-evolve` 로 조정한다고 알린다.

### 1-4. 답을 구성으로 옮기기
| 답 | 반영 |
|---|---|
| 세부 도메인 | 핵심 동작마다 그 품질을 책임질 역할을 정한다. 3장에 비슷한 유형이 있으면 그 구성에서 출발하고, 없으면 2장의 공통 역할 + 도메인 전용 역할을 직접 설계한다 (`team-design.md` 4장 템플릿). "가장 어려운 부분"은 전용 역할이나 도메인 점검 항목으로 반드시 반영한다 |
| 단계: 새로 만든다 | 설계 역할(architect, designer)을 계획 단계에 연결 |
| 단계: 개선 | eval-designer로 **기준선부터** 만든다. 기준선이 없으면 개선인지 알 수 없다 |
| 단계: 품질 문제 | eval-designer + 원인 분석을 우선. 실패 사례를 eval 케이스로 먼저 고정 |
| 우선순위: 정확성·근거 | eval-designer를 검증 단계에 필수로 |
| 우선순위: 안전성·권한 | safety-reviewer 추가 |
| 우선순위: 비용·지연 | cost-latency-analyst 추가 |
| 우선순위: 평가 자동화 | eval 실행을 도메인 워크플로로 묶는다 (반복 가능하게) |
| 규모 | 가볍게: 기본 구성에서 가장 중요한 1~2명. 철저하게: 검증 역할에 반박 검증 추가 |

## 2. 공통 역할

거의 모든 AI Agent 프로젝트에 필요하다. 유형별 구성은 이 역할을 재사용한다. 같은 역할을 이름만 바꿔 또 만들지 않는다.

### `team-prompt-engineer` — opus
- **맡는 일**: 시스템 프롬프트, 도구 설명, few-shot 예시, 출력 형식의 설계와 개정
- **원칙**
  - 고치기 전에 기준선 eval 결과를 확인한다. 프롬프트 변경은 느낌이 아니라 측정으로 판단한다.
  - `항상`/`절대` 규칙 나열 대신 이유를 쓴다. 모델도 이유를 알아야 예외 상황에서 맞게 판단한다.
  - 한 번에 한 가지만 바꾼다. 여러 개를 바꾸면 무엇이 효과였는지 모른다.
  - 프롬프트는 코드와 함께 버전 관리되는 위치에 둔다.
- **호출 시점**: 계획 (프롬프트가 바뀌는 작업), 프롬프트 개선 요청
- **모델 근거**: 의도와 모델 행동을 함께 추론해야 하는 설계 작업

### `team-eval-designer` — opus
- **맡는 일**: 골든 셋, 채점 기준 (코드 assertion, LLM-judge 루브릭), 회귀 eval 실행과 변경 전후 비교
- **원칙**
  - 객관적으로 판정할 수 있는 것은 코드 assertion으로, 그렇지 않은 것만 LLM-judge로 채점한다.
  - LLM-judge는 루브릭과 예시를 고정하고, 일부를 사람 판정과 대조해 믿을 만한지 확인한다.
  - eval 케이스는 실제 실패 사례와 경계 사례에서 만든다. 쉬운 케이스만 있으면 항상 통과한다.
  - 결과는 변경 전후 비교로 보고하고, 표본 수와 실행 간 편차를 함께 적는다. 표본이 작으면 차이를 단정하지 않는다.
  - 단위 테스트에서는 LLM 호출을 고정(mock 또는 녹화)하고, 실제 호출 eval은 따로 둔다. 비결정적 테스트가 CI를 흔들지 않게 하기 위해서다.
- **호출 시점**: 검증 (프롬프트, 모델, 도구, 검색이 바뀔 때), 품질 문제 조사
- **모델 근거**: 근거를 대조해 판정하는 교차 검증

### `team-safety-reviewer` — opus, 읽기 전용
안전성이 우선순위이거나, 에이전트가 외부에 쓰기·결제·삭제·발송을 할 수 있을 때 둔다.
- **맡는 일**: 프롬프트 인젝션, 도구 권한, 되돌릴 수 없는 동작, 비밀·개인정보 노출 검토. 파일은 수정하지 않는다 (`disallowedTools`).
- **원칙**
  - 도구 출력, 검색 문서, 웹 페이지, 사용자 업로드가 지시가 아니라 데이터로 다뤄지는지 확인한다.
  - 파괴적이거나 외부로 나가는 도구에 확인 단계, dry-run, 최소 권한이 있는지 본다.
  - API 키와 개인정보가 프롬프트, 로그, 트레이스에 남지 않는지 본다.
- **호출 시점**: 검증 (도구, 권한, 외부 입력 경로가 바뀔 때)

### `team-cost-latency-analyst` — sonnet
비용·지연이 우선순위일 때 둔다.
- **맡는 일**: 토큰 사용량, 호출 수, prompt caching, 모델 티어, 스트리밍, 병렬화 분석
- **원칙**
  - 추정이 아니라 측정한다 (응답의 usage 필드, 로그, 트레이스).
  - 품질 eval 결과와 함께 보고한다. 비용만 줄고 품질이 떨어지면 개선이 아니다.
- **호출 시점**: 검증 (모델, 호출 구조가 바뀔 때), 비용·지연 개선 요청

## 3. 유형별 구성 예시

자주 만나는 유형의 출발점이다. 사용자의 도메인이 여기 없거나 여러 유형에 걸치면 핵심 동작별로 역할을 직접 설계한다. 새 도메인으로 만든 팀이 잘 동작했다면 이 장에 예시로 추가해 다음 설계의 출발점으로 쓴다.

### A. 대화형·RAG
- **기본 구성**: prompt-engineer + eval-designer + `team-retrieval-engineer` (sonnet)
- **retrieval-engineer**: 청킹, 임베딩, 인덱싱, 하이브리드 검색, 리랭킹을 맡는다.
  - 검색 품질(recall@k 등)과 답변 품질을 따로 측정한다. 어느 단계의 문제인지 알아야 고칠 수 있다.
  - 답변에 출처가 이어지도록 메타데이터를 유지한다.
- **검증 연결**: 검색이나 프롬프트가 바뀌면 eval-designer가 검색 지표와 답변 근거성을 함께 본다.
- **도메인 점검**: 근거 없는 답변 처리, "모른다"고 답하는 경로, 문서가 바뀔 때 재색인 경로.

### B. 도구 사용·업무 자동화 (function calling, MCP)
- **기본 구성**: prompt-engineer + eval-designer + `team-tool-designer` (opus). 쓰기 도구가 있으면 safety-reviewer를 더한다.
- **tool-designer**: 도구 스키마, 이름, 설명, 에러 응답 형식, MCP 서버를 맡는다.
  - 도구 설명도 모델이 읽는 프롬프트다. 언제 쓰고 언제 쓰지 않는지 적는다.
  - 에러는 모델이 다음 행동을 고를 수 있게 원인과 해결 힌트를 담아 반환한다.
  - 비슷한 도구를 늘리지 말고 매개변수로 묶는다. 도구가 많을수록 선택 오류가 는다.
  - 멱등성, 타임아웃, 재시도 정책을 정한다.
- **검증 연결**: 궤적 eval (올바른 도구를 올바른 인자로, 불필요한 호출 없이 쓰는가), 도구 실패를 주입한 테스트.
- **도메인 점검**: 도구 루프 상한, 부분 실패 후 상태, 파괴적 동작의 확인 단계.

### C. 멀티에이전트 오케스트레이션
- **기본 구성**: `team-agent-architect` (opus) + prompt-engineer + eval-designer
- **agent-architect**: 역할 분해, 토폴로지 (파이프라인, 분산·통합, 감독자 등), 에이전트 사이 입출력 계약, 상태·메모리, 실패 처리를 맡는다.
  - 단일 에이전트로 충분한지 먼저 따진다. 에이전트 수만큼 비용과 실패 지점이 는다.
  - 에이전트 사이에 주고받는 데이터는 스키마로 정한다.
  - 하위 에이전트가 실패하면 결과에서 빠졌다는 사실을 드러낸다. 조용히 빠지면 결과를 믿을 수 없다.
  - 위임 계층은 2단계 이내로 둔다.
- **검증 연결**: 계약 대조 (생산 에이전트의 출력 ↔ 소비 에이전트의 입력), 종단 eval.
- **도메인 점검**: 에이전트 간 무한 위임·반복 상한, 부분 실패 시 결과 처리, 에이전트별 비용.

### D. Claude Code 확장 (스킬, 서브에이전트, 훅, 플러그인)
- **기본 구성**: `team-skill-author` (sonnet) + eval-designer
- **skill-author**: SKILL.md, 에이전트 정의, 훅 스크립트, 플러그인 매니페스트를 맡는다.
  - description에 하는 일, 호출 조건, 쓰지 않는 경우를 적는다.
  - SKILL.md는 500줄 미만으로 두고 세부는 `references/` 로 옮긴다. 반복 실행 코드는 `scripts/` 에 둔다.
- **검증 연결**: 호출 조건 테스트 (불러야 할 요청 + 비슷하지만 다른 경계 사례), 스킬 적용 vs 미적용 비교.
- **도메인 점검**: 훅 실패 시 동작 (막을지 통과시킬지), 도구 제한이 의도대로인지.

### E. 음성·실시간
- **기본 구성**: prompt-engineer + eval-designer + `team-latency-engineer` (sonnet)
- **latency-engineer**: 스트리밍, 첫 응답 지연, 끼어들기, 턴 감지, 연결 끊김 복구를 맡는다.
  - 구간별 지연(STT → LLM → TTS)을 따로 측정한다.
- **검증 연결**: 지연 예산 대비 측정, 끼어들기·침묵·잡음 시나리오.
- **도메인 점검**: 짧고 말하기 좋은 응답 형식, 중간에 끊긴 응답의 상태 처리.

### 혼합
주 유형의 구성에 보조 유형의 핵심 역할 하나만 더한다. 공통 역할은 한 번만 만든다.

## 4. AI Agent 공통 점검 항목

domain.md 의 "도메인 점검"에는 이 가운데 해당 유형에 맞는 것만 옮긴다. 모두 옮기면 매 세션 컨텍스트만 차지한다.

- 모델 ID와 매개변수가 현재 유효한가. Anthropic SDK를 쓰면 기억에 의존하지 말고 `claude-api` 스킬로 확인한다.
- 프롬프트, 모델, 도구가 바뀐 변경에 eval 비교 결과가 있는가.
- 외부 입력 (도구 출력, 검색 문서, 웹)이 지시로 실행되는 경로가 없는가.
- LLM 호출 실패 (429, 타임아웃, 잘린 출력)를 처리하는가.
