# 팀 설계와 생성

도메인 팀(`team-*`)을 설계하고 파일로 만드는 방법이다. [revfactory/harness](https://github.com/revfactory/harness) v2의 설계 원칙을 이 하네스 구조에 맞게 줄였다.

## 목차
1. 이름과 위치
2. 실행 모드
3. 모델 선택
4. 에이전트 정의 템플릿
5. 도메인 워크플로(오케스트레이터) 스킬 템플릿
6. domain.md 에 연결하기
7. 생성 후 검증

---

## 1. 이름과 위치

| 산출물 | 위치 | 업데이트 시 |
|---|---|---|
| 공통 기반 | `.claude/agents/harness-*`, `.claude/skills/harness-*` | 템플릿으로 교체 |
| 도메인 팀 에이전트 | `.claude/agents/team-{role}.md` | 보존 |
| 도메인 워크플로 스킬 | `.claude/skills/team-{name}/SKILL.md` | 보존 |
| 팀 구성과 연결 | `.harness/context/domain.md` | 보존 |
| 중간 산출물 | `.harness/workspace/{phase}_{agent}_{artifact}.md` | 보존 |

- `team-` 접두사가 있어야 하네스 파일로 인식되어 git ignore, doctor 점검, 제거 대상이 된다.
- 에이전트에는 **누가** 일하는지를, 스킬에는 **어떻게** 하는지를 적는다. 둘을 섞으면 같은 절차가 여러 에이전트에 복사되어 따로따로 낡는다.
- 새로 만들기 전에 기존 `harness-*`, `team-*`, 프로젝트 고유 에이전트와 역할이 겹치는지 확인한다. 겹치면 기존 것을 쓰거나 확장한다. 같은 역할이 이름만 달리해 쌓이면 무엇이 호출될지 예측할 수 없다.

## 2. 실행 모드

작업 흐름의 모양으로 고른다. 팀 크기로 고르지 않는다.

| 모드 | 사용하는 기능 | 알맞은 작업 |
|---|---|---|
| 서브에이전트 위임 | `Agent` 한 번 호출 (독립 작업은 한 메시지에 병렬) | 결과만 한 번 받으면 되는 작업. **기본값** |
| 지속형 에이전트 | `Agent(name:)` + `SendMessage` | 같은 전문가와 피드백을 여러 번 주고받는 작업 (예: 프롬프트 초안 ↔ 평가 반복) |
| 워크플로 | `Workflow` 스크립트 (`pipeline`, `parallel`, `schema`) | 처리 목록과 반복 조건을 코드로 정할 수 있는 작업 (예: eval 케이스 N개 채점, 지적마다 반박 검증) |

- 단계마다 성격이 다르면 섞는다. 워크플로 스킬의 각 단계 위에 `**실행 모드:**` 를 적는다.
- `Workflow` 는 사용자가 명시적으로 요청했거나, 사용자가 그 워크플로 스킬을 직접 불렀을 때만 쓴다. 비용이 크기 때문이다.

## 3. 모델 선택

에이전트의 중요도가 아니라 업무 성격으로 고르고, 이유를 frontmatter 주석으로 남긴다.

| 모델 | 업무 |
|---|---|
| fable | 스스로 계획해 여러 단계를 장기간 자율 실행. 팀 에이전트에는 드물다 (조율은 메인 세션이 맡는다) |
| opus | 범위가 정해진 깊은 분석: 설계, 교차 검증, 평가 판정, 프롬프트 설계 |
| sonnet | 절차가 분명한 작업: 구현 보조, 측정, 형식 변환, 로그 분석. **애매하면 sonnet** |

모든 에이전트를 opus로 지정하지 않는다. 비용만 늘고 품질 차이는 업무에 따라 없을 수 있다.

## 4. 에이전트 정의 템플릿

```markdown
---
name: team-{role}
description: {하는 일 한두 문장}. {어느 단계·어떤 요청에서 호출되는지}. {쓰지 않는 경우와 대신 쓸 에이전트}.
# {모델}: {업무 성격에 따른 선택 이유}
model: {opus|sonnet}
# 읽기 전용 검토자만:
# disallowedTools: Edit, Write, MultiEdit, NotebookEdit
---

# team-{role} — {역할 한 줄}

너는 이 프로젝트({도메인 유형})의 {역할}이다.

## 핵심 역할
1.
2.

## 작업 원칙
- 원칙 — 이유. (이유가 있어야 예외 상황에서도 같은 기준으로 판단한다)

## 입력·출력
- 입력: 호출자가 넘기는 것, 읽을 파일 (`.harness/context/domain.md` 포함)
- 출력: 반환 형식. 파일로 넘길 때는 `.harness/workspace/{phase}_{agent}_{artifact}.md`
- 최종 메시지가 곧 호출자에게 주는 반환값이다.

## 다시 호출할 때
- 이전 산출물과 피드백이 오면 지적된 부분만 고친다.

## 오류 처리
- 입력이 없거나 모호할 때:
- 같은 실패가 반복될 때: 두 번째 실패 후 멈추고 시도한 방법과 가설을 보고한다.

## 협업
- 다른 에이전트와의 관계 (누구의 출력을 받고, 누구에게 넘기는가)
```

- 읽기 전용 검토 에이전트는 `disallowedTools` 로 수정 도구를 막는다. 셸은 남겨 git, 테스트를 실행할 수 있게 한다.
- 파일을 고치는 에이전트에서 도구를 제한할 때는 Write와 Edit를 함께 준다. Edit가 없으면 한 줄을 고칠 때도 파일 전체를 다시 써야 해서 수정을 포기하고 우회한다.
- 원칙에는 이 프로젝트에서 확인한 사실(경로, 명령, 기존 패턴)을 넣는다. 일반론만 있으면 기본 에이전트와 다를 게 없다.

## 5. 도메인 워크플로(오케스트레이터) 스킬 템플릿

팀 에이전트를 한 흐름으로 묶어야 하는 반복 작업이 있을 때만 만든다 (예: 프롬프트 개선 사이클, eval 회귀 실행). 기본 루프(plan → verify → handoff)로 충분하면 만들지 않는다.

```markdown
---
name: team-{name}
description: {무엇을 하는 흐름인지}. "{호출 표현}", "{호출 표현}" 같은 요청에 사용. "다시 실행", "{부분}만 다시", "이전 결과로 개선" 같은 후속 요청에도 사용. {쓰지 않는 경우}.
---

# {흐름 이름}

## 0. 이전 실행 확인
- `.harness/workspace/` 에 이번 흐름의 산출물이 있고 일부만 고치는 요청이면 해당 단계만 다시 실행한다.
- 새 입력이면 기존 산출물을 `.harness/workspace/_prev_{YYYYMMDD-HHmm}/` 로 옮기고 처음부터 실행한다.

## 1. {단계} — 실행 모드: 서브에이전트
- 담당: `team-...`
- 입력 / 출력 파일:

## 2. {단계} — 실행 모드: ...

## 데이터 전달
| 단계 | 생산 | 소비 | 형식 |

## 오류 처리
- 실패한 단계는 한 번 다시 시도한다. 또 실패하면 그 결과 없이 진행하고 보고에 누락을 적는다.
- 권한 거부, 인증 만료, 사용량 한도는 재시도하지 않는다.
- 에이전트가 남긴 빈 곳을 추측으로 채우지 않는다. 직접 확인한 사실만 반영한다.

## 테스트 시나리오
- 정상 흐름: {구체적인 요청} → {기대 결과}
- 오류 흐름: {실패 상황} → {기대 동작}
```

AI Agent 도메인에서 자주 쓰는 흐름: **개선 사이클** — 기준선 eval → 변경 (prompt-engineer 등) → 같은 eval 재실행 → 전후 비교 보고. 기준선 없이 바꾸면 개선인지 악화인지 알 수 없다.

## 6. domain.md 에 연결하기

`/harness-plan` 과 `/harness-verify` 는 템플릿 사본이라 팀 에이전트 이름을 모른다. 대신 실행할 때 domain.md 의 "루프 연결"을 읽는다. 그러므로 팀 에이전트는 반드시 domain.md 에 연결해야 실제로 호출된다.

- **팀** 표: 모든 `team-*` 에이전트와 워크플로 스킬을 백틱으로 적는다. doctor.ps1 이 이 표와 실제 파일을 대조한다.
- **루프 연결**: "어떤 변경이면 → 어떤 에이전트를 → 무엇을 위해" 형식으로 쓴다. 조건 없이 "항상"이라고 쓰면 작은 수정에도 비싼 에이전트가 돈다.
- **도메인 점검**: `ai-agent-domains.md` 4장에서 이 유형에 해당하는 항목만.
- **변경 이력**: 날짜, 변경, 대상, 사유. 팀을 만들거나 바꿀 때마다 한 줄.

## 7. 생성 후 검증

1. doctor.ps1 — 팀 표와 파일 일치, frontmatter의 `name` 이 파일·폴더 이름과 같은지.
2. 각 에이전트 description을 서로 비교해 호출 조건이 겹치지 않는지 본다. 겹치면 "쓰지 않는 경우"로 경계를 긋는다.
3. 워크플로 스킬이 있으면 호출 조건을 시험할 요청을 만든다: 불러야 할 요청 3개 이상, 표현이 비슷하지만 다른 스킬을 써야 하는 경계 사례 3개 이상. 명백히 무관한 요청은 경계를 시험하지 못한다.
4. 모의 실행: 워크플로의 단계 순서, 각 단계 입력이 앞 단계 출력과 맞는지, 오류 시 대체 절차를 실제로 실행할 수 있는지 읽어서 확인한다.
