# 하네스 회고·개선

하네스는 쓰면서 고친다. 무엇이 반복해서 어긋났는지 찾아, 다음 세션부터 같은 일이 생기지 않도록 규칙으로 남긴다.

## 반영 위치

`.claude/agents/harness-*`, `.claude/skills/harness-*`, `.harness/HARNESS.md`, `.harness/hooks/` 는 템플릿 사본이라 하네스를 업데이트하면 덮어써진다. 그래서 피드백 성격에 따라 반영 위치를 나눈다.

| 피드백 성격 | 반영 위치 |
|---|---|
| 이 프로젝트에만 해당하는 규칙 (스타일, 금지 사항, 도구 사용법) | `.harness/context/conventions.md` 의 "학습된 규칙" |
| 프로젝트 목표·구조에 대한 오해 | `.harness/context/project.md`, `architecture.md` |
| 검증 명령이 틀렸거나 너무 느림 | `.harness/harness.config.json` |
| 도메인 팀의 결과 품질, 원칙, 호출 조건 | 해당 `.claude/agents/team-*.md`, `.claude/skills/team-*/` (프로젝트 파일이라 직접 고친다) |
| 팀 에이전트가 너무 자주·드물게 호출됨 | `.harness/context/domain.md` 의 "루프 연결" 조건 |
| 모든 프로젝트에 해당하는 하네스 동작 (공통 에이전트, 스킬 절차, 훅) | 템플릿 원본 `{{TEMPLATE_DIR}}` |
| 모든 AI Agent 프로젝트에 해당하는 팀 설계 지식 | 템플릿 원본의 `global-skill/harness/references/` |

에이전트를 새로 추가하거나 지우거나, 도메인 유형을 바꾸는 일은 이 스킬이 하지 않는다. 전역 `harness` 스킬로 "에이전트 추가해줘", "팀 재구성해줘"라고 요청하도록 안내한다. evolve는 기존 구성을 조정하는 데 집중한다.

템플릿 원본은 다른 프로젝트에도 영향을 준다. 바로 고치지 말고 바꿀 내용을 사용자에게 보여주고 확인받는다. 고친 뒤에는 "하네스 업데이트"로 각 프로젝트에 반영된다.

## 절차

1. **수집**
   - 사용자가 준 피드백을 정리한다. 없으면 이번 세션에서 신호를 찾는다: 사용자가 같은 종류의 수정을 두 번 이상 요구한 것, 같은 lint·test 실패의 반복, 사용자가 하네스 스킬을 거치지 않고 직접 처리한 작업.
   - `.harness/state/decisions.md`, `progress.md` 의 "막힌 것", `conventions.md` 의 기존 학습된 규칙을 읽는다.
   - 피드백도 신호도 없으면 억지로 만들지 않는다. "반영할 것 없음"으로 끝낸다.
2. **일반화** — 사례 하나에 규칙 하나를 붙이지 않는다. 왜 그런 일이 생겼는지 찾아 원리로 쓴다. 사례마다 규칙을 붙이면 문서가 규칙 더미가 되고, 비슷하지만 다른 상황에는 적용되지 않는다.
   - 나쁜 예: "`UserService.ts` 에서 any 쓰지 마."
   - 좋은 예: "외부 API 응답은 `src/types/api` 의 타입으로 파싱한다. any 로 받으면 필드 이름 불일치가 런타임까지 숨는다."
   - 규칙마다 이유를 함께 쓴다. 이유를 알아야 예외 상황에서도 올바르게 판단한다.
3. **충돌 확인** — 기존 규칙이나 `decisions.md` 의 결정을 뒤집는 방향이면 상충을 알리고 확인받는다. 예전에 "짧게"로 고쳤는데 이번에 "길게"라는 피드백이 왔다면 둘 다 만족하는 기준을 찾는다.
4. **반영** — 한 번에 하나씩 반영한다. 여러 개를 한꺼번에 넣으면 어떤 변경이 효과가 있었는지 알 수 없다.
   - `conventions.md` 에 "학습된 규칙" 섹션이 없으면 파일 끝에 만든다.
   - context 문서는 매 세션 로드되므로 짧게 유지한다. 더 이상 맞지 않는 규칙은 지운다.
5. **기록** — `decisions.md` 에 `## YYYY-MM-DD: 하네스 개선 — 제목` 으로 맥락(어떤 피드백이었나), 결정(무엇을 바꿨나), 대안을 남긴다. 도메인 팀(`team-*`)이나 루프 연결을 바꿨다면 `domain.md` 의 "변경 이력" 표에도 한 줄 남긴다. 이력이 쌓여야 같은 논의가 되풀이되지 않는다.
6. **보고**
   - 반영한 변경과 일반화 근거
   - 반영하지 않은 피드백과 이유
   - 템플릿 원본에 제안하는 변경 (있다면)
