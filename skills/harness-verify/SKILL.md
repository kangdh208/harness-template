# 검증

## 1. 범위 파악
HARNESS.md 의 "내 작업 범위"에 따라 내 변경 파일 목록을 만든다.
- git 저장소면 `git status --porcelain` + `git diff --name-only @{u}..HEAD` (upstream이 없으면 `git diff --name-only HEAD`)
- 아니면 이번 세션에서 수정한 파일

## 2. 기계 검증
`.harness/harness.config.json` 을 읽는다.
- `lint`: `{file}` 이 있으면 내 변경 파일마다 실행한다. 없으면 프로젝트 전체를 실행하되, 내 변경 파일에서 나온 오류만 고칠 대상으로 삼는다.
- `test`: 실행한다. 실패는 내 변경과 관련된 것(내가 바꾼 코드나 그 호출부)과 범위 밖(팀원 코드에서 원래 실패하던 것)으로 나눈다. 판단이 애매하면 변경 전 상태(upstream 브랜치의 CI 결과 등)를 근거로 삼는다. 작업 트리를 stash하거나 되돌려서 확인하지 않는다. 그래도 모르면 범위 밖으로 두고 보고한다.
- 비어 있는 명령은 실행하지 않고 "미검증"으로 기록한다.

## 3. 리뷰
다음 중 하나라도 해당하면 `harness-reviewer` 를 호출한다. 변경 파일 목록과 작업 목표를 함께 넘긴다.
- 여러 파일이 바뀌었다.
- 핵심 로직, 공개 API, 데이터 구조, 모듈 사이 연결 지점이 바뀌었다.
- 사용자가 리뷰를 요청했다.

`.harness/context/domain.md` 의 "루프 연결 — 검증"에서 이번 변경에 해당하는 조건을 찾아 도메인 팀 에이전트(`team-*`)도 호출한다 (예: 프롬프트가 바뀌었으면 eval 담당). 조건에 해당하지 않으면 부르지 않는다. 비싼 검증을 작은 수정마다 돌리지 않기 위해서다.

테스트(`harness-tester`), 리뷰, 도메인 검증은 서로 결과를 기다릴 필요가 없으므로 한 메시지에서 병렬로 맡긴다.

## 4. 수정과 재검증
- 내 변경과 관련된 실패와 `확인됨` 지적은 고친 뒤 2단계부터 다시 실행한다. 범위 밖 실패는 고치지 않는다. `추정` 지적은 직접 확인한 뒤 고칠지 판단한다.
- 최대 3회까지만 반복한다. 그 뒤에도 남은 문제는 더 손대지 말고 보고한다. 같은 문제를 계속 건드리면 다른 곳이 망가질 위험이 커진다.

## 5. 보고
```
통과: 명령 — 결과
실패: 명령 — 실패 출력 핵심
범위 밖 실패: 내 변경과 무관한 실패 (팀원 코드) — 고치지 않음
미검증: 무엇을, 왜 검증하지 못했는가
리뷰: 지적 수 / 고친 것 / 남긴 것과 이유
도메인 검증: 호출한 team-* 와 결과 (예: eval 기준선 대비 변화)
```

검증 명령이 비어 있으면 그 사실을 알리고, 프로젝트에 맞는 명령을 찾아 `harness.config.json` 에 채울지 제안한다.
